## Команди

Windows: у новому шеллі `node`/`npx` часто нема на PATH — спершу
`$env:Path = "C:\Program Files\nodejs;" + $env:Path` (PowerShell) або
`export PATH="/c/Program Files/nodejs:$PATH"` (Git Bash).

- Dev-сервер — **скіл `/restart-dev`**, не `npm run dev` напряму (залиплий
  `node` дає `EPERM … .next\dev`). Прод-збірка локально: зупинити dev (вони
  ділять `.next`), `npx next build`, `npx next start -p 3002`.
- `npm run lint` — ESLint; `npx tsc --noEmit -p .` — типи (лише нові
  `.ts/.tsx`, `checkJs:false`).
- `npm test` — усі тести (vitest, `**/*.test.{js,ts}`); один файл —
  `npx vitest run lib/auth.test.js`; один тест —
  `npx vitest run lib/auth.test.js -t "назва"`; `npm run test:watch`.
- `npx prisma validate` / `npx prisma generate` (`postinstall` генерує сам);
  міграції на реальних даних — **скіл `/db-migrate`**, ніколи `migrate reset`.
- Pre-commit (husky): `lint-staged` (eslint --fix) і відмова, якщо в коміті є
  файл у невідомій теці верхнього рівня чи `.pptx/.docx/.xlsx/.pdf`.
- CI (`.github/workflows/ci.yml`): `prisma validate`, lint, test, build, окремий
  job `api-diff` (`oasdiff` по `openapi.yaml`). `lib/openapi.test.ts` валить
  тести, якщо `app/api/**/route.*` розійшовся зі специфікацією.
- Агенти проєкту (`.claude/agents/`): `architecture-guardian` — після змін
  схеми, `design-guardian` — після будь-якого CSS, `request-guardian` — після
  пачки дрібних правок (звіряє, що кожне прохання реально виконано).

## Карта застосунку

Три кабінети з різними входами (деталі — у розділах нижче):

| Кабінет | Маршрути | Вхід | Для кого |
|---|---|---|---|
| Співробітник | `/hub`, `/courses/[slug]`, `/register` | код + PIN на пошту (`lib/auth.js`, cookie `session`) | польові ролі, телефон |
| Керівник | `/manager/*` | та сама сесія, роль `isManagerTier` (`lib/permissions.js`) | SV/ASM/RM, десктоп |
| Адмін | `/admin/*` | окремий `ADMIN_PASSWORD` → `admin_session` (`lib/adminSession.js`), без зв'язку з Employee | T&D |

Ще два канали: Excel через Power Query (`/api/data/*`, Bearer-токен
`AdminApiToken`) і Telegram Mini App (`/tg`, `/api/tg/*`).

**Потік даних сторінки.** Server Component `app/**/page.js` →
`getCurrentUser()` (`lib/session.js`, React `cache()` над
`"use cache: private"`) → функція-огляд у `lib/*Overview.js` /
`lib/employeeProgress.js` (теж `"use cache: private"`,
`cacheLife("minutes")`, у аргументах лише примітиви) → Prisma
(`lib/prisma.js`, singleton на `@prisma/adapter-pg`). Клієнтські `fetch` до
`/api/*` — лише для дій (відповідь у плеєрі, нагадування, підвантаження важких
блоків дашборда). `cacheComponents: true` у `next.config.mjs`; кожен
`page/layout` поки що має `export const instant = false` (TODO adoption).

**Де яка логіка.** Чиста математика — `lib/*.ts` із тестом поруч
(`coursePlan`, `retryPolicy`, `ratingLogic`, `teamInsights`,
`dashboardHeights`, `snakePath`, `pin`); доступ до БД — `lib/*.js`;
`components/` — React, а великі файли (`ManagerDashboard.jsx`,
`AdminCourseEditor.jsx`, `CoursePlayer.jsx`) тримають стан екрана цілком.
`app/generated/prisma` — згенерований клієнт, не редагувати.

**Стилі.** Усі `app/styles/*.css` імпортуються в кореневому `app/layout.js` у
фіксованому порядку (gridstack ДО `manager.css`). Розміри й кольори — лише
токени з `app/styles/tokens.css`; адаптація компонента, що живе і в телефонній
рамці, і в сітці, — `@container`, не `@media`.

**Фонове.** Один cron-маршрут `app/api/cron/check-overdue-enrollments` (у
`vercel.json` на нього два розклади): прострочення, авто-відзнаки,
авто-призначення за `publishAt`, дайджести, ретенція журналу дій.

**Легасі.** `legacy/` — архів vanilla JS + Google Sheets, не розвивається.

# Правила та конвенції проєкту

Цей проєкт мігрує legacy vanilla JS + Google Sheets систему на Next.js +
Prisma + Postgres (Neon). Нижче — рішення й правила, до яких дійшли за
попередню розробку, щоб не переоткривати їх у кожній новій сесії.

## Жорсткі правила (не порушувати без явного дозволу користувача)

- **Поступовий перехід на TypeScript** (рішення користувача, 2026-09-14
  — до цього тут стояло "ніякого TypeScript", проєкт свідомо був на
  чистому JS). Нові файли — `.ts`/`.tsx`. Існуючі `.js`/`.jsx` НЕ
  переписуються масово — мігруються поступово, коли й так лізеш у
  конкретний файл із незв'язаною причиною, а не окремим "рефактор заради
  рефактору" проходом. `tsconfig.json` навмисно `allowJs:true` +
  `checkJs:false` — старий JS лишається валідним і не перевіряється
  заднім числом, лише нові `.ts`/`.tsx` типізуються по-справжньому
  (`strict:true`).
  **Самоперевірка перед комітом:** `git status` не має показувати нових
  `.js`/`.jsx` — 2026-09-15 за одну сесію так з’явилось ~15 нових JS-файлів
  (рейтинг, сповіщення, офлайн), правило просто забулось; чисті модулі
  рейтингу вже переведено (`lib/rating.ts`, `ratingLogic.ts`, `audit.ts`),
  компоненти рейтингу/сповіщень/офлайну — ще `.jsx`, конвертувати по
  касанню.
- **Ніколи не вигадувати дані.** Якщо зв'язок/значення не можна вивести зі
  100% впевненістю з наявних даних — лишати `null`/невизначеним і питати
  користувача, а не писати правдоподібне-але-неперевірене. Це стосується
  особливо організаційної структури (managerId), територій, будь-яких
  зв'язків між реальними людьми. Один раз невірна евристика вже призначила
  реальній людині невірного керівника (детектовано користувачем, що
  особисто знає оргструктуру) — виправлено системно, не тільки для одного
  запису.
- **Ніколи не писати реальні секрети в `.env` самостійно** (DB-паролі,
  API-ключі, токени) — навіть якщо користувач надіслав значення прямо в
  чат і попросив вписати. Користувач вписує сам; можна підказати, куди і
  що саме вписати.
- **Коли потрібна дія користувача — зупинитись і сказати, а не вирішувати
  самому.** Якщо для перевірки чи наступного кроку бракує того, що може
  дати лише користувач (сесія в `/admin` після рестарту dev-сервера, вхід
  під іншим акаунтом, дозвіл на запис у бойову базу, вибір між двома
  рівноцінними варіантами) — назвати це прямо, попередити заздалегідь і
  чекати. Не обходити (не підміняти живу перевірку «проходить збірка»,
  не вибирати варіант «за замовчуванням» мовчки) і не пропускати як
  «перевірю потім». Причина: 2026-09-14 сесія `/admin` злетіла після
  `/restart-dev`, і частина правок лишилась неперевіреною — користувач
  дізнався про це лише з підсумкового чек-листа, а не в момент, коли міг
  просто зайти знову.
- **Не гадати структуру нового Next.js.** `AGENTS.md` (авто-генерується
  `next dev`, не редагувати вручну) — версія тут із breaking changes
  відносно тренувальних даних; звірятись з
  `node_modules/next/dist/docs/`.

- **Сторінки 404 і помилки** (2026-10-05): `app/not-found.tsx` (і `notFound()` у роутах, і
  адреса, якої нема), `app/error.tsx` (клієнтський, кнопка `retry` — у Next 16.2+;
  `unstable_retry`/`reset` лишено запасними) і `app/global-error.tsx` (замінює
  кореневий layout, тому має власні `<html>/<body>` та inline-стилі — глобальні CSS
  і токени сюди не доходять). «На головну» скрізь веде на `/`: `app/page.js` сам
  розводить за роллю (нема сесії → /register, керівник → /manager, решта → /hub).
  Стилі — `app/styles/status-pages.css`.

- **Prisma 7**, закріплено на стабільній `7.10.0` (не `latest` — той тег
  на npm якийсь час указував на нестабільний `8.0.0-rc.*`). Генератор —

  свідомо, заради простоти.
- Windows: `node`/`npx`/`npm` не завжди на `PATH` у новому шеллі — префікс

## Дані та ієрархія

- **Employee.name** пишеться в базу ЛИШЕ з email-адреси
  (`nameFromEmail`), ніколи з введеного вручну імені. Поля «ім'я» на
  вході немає взагалі (прибрано 2026-10-03, вхід — лише код + PIN), і
  в `localStorage` ім'я теж не зберігається; польові ролі без email скрізь
  показуються заглушкою з посади/території (`Employee.name`), в сертифікаті
  теж.
- **Employee.email** є лише в менеджерського шару (SV/ASM/LKAM/RM
  HoReCa/FSM MT/SV RKA), крім ТП RKA (свідомо прибрано, хоч і потрапляв
  під евристику). Польові ролі отримують PIN на пошту `manager.email`.
- **Employee.externalCode** — шукати через `findFirst({ where: {
  externalCode: { equals, mode: "insensitive" } } })`, не `findUnique` —
  код у джерелі в основному UPPERCASE, юзер може ввести як завгодно.
- **Ієрархія (managerId)**: пряме підпорядкування — ASM → SV → ТП → МР.
  RM HoReCa/LKAM/FSM MT/ASM/SV(без ASM)/SV RKA — верхівки своїх гілок,
  managerId навмисно `null` (немає надійного способу резолвити). RM
  HoReCa ↔ SV/ТП HoReCa — dotted-line зв'язок, свідомо не змодельований.
- **Territory** ієрархічна (`parentId`, як і `Employee.managerId`):
  RM-регіон → ASM-область → SV-район/місто. Назва вузла = "посада +
  територія" одним рядком ("ASM Сумська область") — ім'я людини в
  дужках з джерела НІКОЛИ не пишеться в базу, лише як ключ зіставлення
  під час імпорту.
- Зіставлення кирилиця→база при імпорті — фамілія обов'язково, ім'я лише
  як тай-брейк при кількох однофамільцях; ніколи не по самому імені.
  Транслітерація в реальних даних нестабільна (одна й та сама буква різні
  люди пишуть по-різному) — покладатись на це не можна.

## Курси (Course → Module → Screen → Component)

- Ієрархія контенту: **Course → Module → Screen → Component**, не
  пласка Course → Module. (До 2026-09 рівні називались
  Course → Block → Module → Lesson — перейменовано: старий Block став
  Module, старий Module став Screen, старий Lesson став Component; див.
  `///`-коментар при `model Module` у `schema.prisma`.) Module —
  угруповання для навігації, Enrollment рахується по Course в цілому, не
  по модулю.
- **"Пауза між модулями"** (`Module.cooldownDays`) — наступний модуль
  відкривається лише після того, як склали (80%+) усі тести
  ПОПЕРЕДНЬОГО (`ModuleCompletion.passed=true`), і минула пауза, що
  рахується від РЕАЛЬНОЇ дати складання (`ModuleCompletion.completedAt`),
  а не від дати призначення курсу. Окремого календарного механізму
  (колишній `unlockAfterDays`, рахував від дати ПРИЗНАЧЕННЯ курсу) в
  схемі більше нема — прибрали (2026-09), лишився лише
  completion-based `cooldownDays`.
  **Сесія плеєра** (`lib/courseContent.js getSessionModules`, 2026-09-15):
  модулі без паузи йдуть ланцюжком в одному проходженні з чекпоінтом
  «Модуль складено / не складено» між ними; на модулі з `cooldownDays`,
  чий попередник ще не складено, сесія зупиняється — плеєр показує
  чекпоінт з «На головну» і НЕ шле `/submit`. Курс `completed` лише коли
  кожен модуль має `ModuleCompletion` (`/submit` віддає 409 інакше). До
  цього плеєр брав лише модулі, чий попередник уже в базі, і 5-модульний
  курс ставав «completed» після першого модуля.
- **Темп курсу (2026-09-17, «Розклад» у конструкторі):** `Course.moduleDays`
  (рекомендовано днів на модуль) і `Course.modulePauseDays` (мінімальна
  пауза перед наступним модулем, дефолт для модулів без власного
  `cooldownDays`). Модель як у Coursera: дати по модулях М'ЯКІ
  (k-й модуль «до assignedAt + k×moduleDays», без штрафу, лише «за
  графіком / відстаєте»), жорсткий — один `deadlineDays`. Уся математика
  — `lib/coursePlan.ts` (чиста, з тестами), і ту саму функцію рендерять
  три місця: план у плеєрі (`components/CoursePlan.tsx`), методичка і
  калькулятор у конструкторі (`components/CoursePacingCalculator.tsx`) —
  прев'ю не може розійтись із плеєром. Ефективна пауза для сесії плеєра —
  `moduleCooldownDays(course, module)` у `lib/courseContent.js`; нову
  перевірку доступності писати через неї, а не читати `cooldownDays`
  напряму.
  **Показ плану (2026-09-17, П'ЯТА ітерація — за глибоким аналізом
  світової практики (Duolingo path, vertical-stepper/timeline патерни) і
  живого користування четвертою).** Два принципово різних режими, не
  один що адаптується:
  - **Мобільний (база, нижче `@container cp-card` min-width:640px) —
    ЛІВА РЕЙКА**, класичний vertical-stepper: колонка кольорових
    кружечків-статусів по лівому краю (`.cp-plan-cell` —
    `display:flex; flex-direction:row`), лінія йде крізь них зверху
    вниз, картка — блок справа на всю решту ширини
    (`.cp-plan-square{flex:1 1 auto}`). Геометрія не потребує спеціального
    коду — колонка X одна й та сама для всіх точок (dx=0), і
    `lib/snakePath.ts` вже малює пряму вертикальну лінію без переносів
    рядка в цьому випадку. Раніше (четверта ітерація) тут був верхній
    «флагшток», зсунутий у стовпчик — тултип по ховеру був фізично
    недосяжний (нема ховера, тап одразу відкриває курс), а «флагшток»
    над карткою на вузькому екрані не читався.
  - **Десктопний (`@container cp-card`, min-width:640px) — «флагшток»**:
    маленька крапка на лінії, коротка ніжка вниз, великий кольоровий
    кружечок статусу нижче (наполовину на картці) — крапка навмисно на
    26px ВИЩЕ верху картки, інакше лінія зливається з рамкою. Картки в
    ряд ЗА КОНТЕНТОМ (`flex-wrap`, не жорсткі CSS grid-колонки): скільки
    влазить за шириною тексту, стільки й стає, без штучного мінімуму
    ширини картки.
  - **Вимірювання вузла** (`useLayoutEffect` у `CoursePlan.tsx`) —
    `getBoundingClientRect()` САМОГО елемента `.cp-plan-dot` (він один
    існує в обох режимах, CSS лише переставляє його) — НЕ обчислена
    офсетом координата: жодних магічних чисел, які треба тримати в парі
    з CSS.
  - **Колірна схема — «світлофор без червоного»**: пройдено — зелений
    (`--cb-success`), доступно/наступний — синій `--cb-notification`
    (НЕ `--cb-secondary` — той теж зелений, фірмовий акцент Carlsberg;
    той самий колір для "пройдено" і "доступно" — якраз пастка, на яку
    свого часу наступив сам Duolingo, наплутавши активний і завершений
    стан однаковим зеленим), провалено/потрібен повтор — бурштиновий
    `--cb-alert` (не `--cb-fail`/червоний: ~8% чоловіків не відрізняють
    червоний від зеленого, і червоний семантично читається як «стоп,
    назавжди», що хибно для стану «спробуй ще раз»), закрито — сірий.
    Малий кружечок на лінії теж пофарбований у колір стану.
  Геометрію переходу рядка (тільки в десктопному режимі) рахує чиста
  функція `lib/snakePath.ts` (з тестами) — приймає реальні координати
  (виміряні через `ResizeObserver`, бо кількість карток у ряду за
  контентом наперед невідома). Перехід рядка рахується від
  НАЙНИЖЧОЇ картки ВСЬОГО ряду, що закінчився (`rowBottom`, максимум по
  ряду — `SnakePoint`), а НЕ від середини відстані між станціями і не
  лише від rowBottom останньої картки перед переносом: картки в ряду
  тепер різної ширини/висоти за контентом (flex-wrap), і сусідня, не
  остання картка того самого ряду може виявитись вищою — інакше лінія
  переходу знову ховається під нею (`z-index` картки вищий за SVG).
  Зелений прогрес — окремий `<path>` з `pathLength={1}` і
  CSS-transition на `stroke-dashoffset` (1→0), лінія «впирається» точно
  у вузол першого непройденого/закритого модуля (`buildProgressPath`,
  зупиняється на `plan.nextModuleId`).
  Другорядні дані модуля: ОДНА найважливіша деталь (час/бал/причина
  блокування, `moduleSubtitle`) ПРЯМО на лицьовій стороні картки завжди
  (і мобільний, і десктоп) — це не залежить від ховера. Повний набір
  (дата складання, пауза перепроходження, рекомендована дата, підпис
  дії) — ЛИШЕ на десктопі по наведенню/фокусу картки (`.cp-plan-tip`,
  `display:none` на мобільному повністю): там ховера не існує фізично,
  ховати за ним хоч щось сенсу нема.
  **«Почати» з плану = `?module=N`** — обраний модуль грається сам, і
  плеєр стартує ОДРАЗУ з його першого екрана (вступ із планом — це те,
  звідки людина прийшла). `page.js` ставить `key` на `<CoursePlayer>`
  (`module-N` / `session`): без нього Next робить клієнтську навігацію в
  той самий маршрут, компонент лишається зі старим станом (idx на вступі,
  чужі answers, ефект відновлення вже відпрацював) — і «Почати» виглядало
  так, ніби нічого не сталось (2026-09-17). Одиночний модуль localStorage
  не читає й не пише: там лежить idx ПОВНОЇ сесії, який у сесії з одного
  модуля показує в порожнечу.
- **Перескладання проваленого модуля (2026-09-17).** Дефолт лишається
  «повтор одразу» — це навчання на освоєння, а не сертифікаційний іспит.
  Але щоб «відповідай, поки не вгадаєш» не перетворювалось на перебір
  варіантів, у конструкторі є три регулятори: `Course/Module.retryFreeAttempts`
  (спроб підряд без паузи), `Course/Module.retryCooldownHours` (пауза
  після них, у ГОДИНАХ) і `Module.questionPoolSize` (скільки випадкових
  питань модуля показувати за спробу). Поля модуля перекривають курс
  (`??`, тож 0 — це усвідомлений нуль, а не «успадкувати»). Уся логіка —
  `lib/retryPolicy.ts` (`resolveRetryRules`, `retryGate`,
  `pickQuestionPool`), з тестами; сервер, план курсу і чекпоінт плеєра
  беруть рішення лише звідти. Вибірка питань робиться в
  `app/courses/[slug]/page.js`, НЕ на клієнті — інакше повний список
  питань приїхав би в браузер. `ModuleCompletion.attemptCount` рахує
  спроби (рядок перезаписується upsert-ом), показується керівнику в
  «Найскладніших модулях» як «у середньому спроб». Лічильник включає й
  ПЕРШУ (провалену) спробу, а `retryFreeAttempts` — це повтори ПІСЛЯ неї
  (`retryGate`: `freeAttempts - (attemptCount - 1)`); інкремент стоїть у
  ДВОХ роутах — `module-complete` і `/submit` (останній модуль курсу йде
  через нього) — новий шлях запису результату модуля має його повторити.
  **Стенд механіки** — `prisma/seed-course-mechanics.js` (`--employee=CODE`,
  `--dry-run`): скидає призначення одного співробітника й створює три
  тестові курси «Механіка 5/10/15» з усіма гейтами (паузи, тижневий замок,
  гальмо перескладання, пул питань, усі 4 типи питань, поріг 50/80/100,
  прострочення). Часові паузи на стенді симулюються зсувом
  `ModuleCompletion.completedAt` одноразовим scratch-скриптом.
- **`Enrollment.status` → `in_progress`** ставить `module-complete` при
  першому результаті по курсу (лише з `not_started`; `overdue` від cron не
  чіпає). До 2026-09-22 цього не робив ніхто: курс із сімома складеними
  модулями лишався «новим» на картці й не потрапляв у фільтр «В процесі».
- **Відновлення в плеєрі** (`localStorage course_progress_<slug>` =
  `{idx, answers, key}`): `key` — підпис набору екранів сесії; чужий
  підпис (наступна сесія з інших модулів) не відновлюється, а стирається.
  На вступі (`idx === introIdx`) нічого не пишеться. Без мережі
  `module-complete`/`/submit` ідуть у `lib/offlineOutbox.js`, і чекпоінт
  показує «збережено на пристрої», а не помилку. Сесія, що впирається в
  паузу або гальмо, закінчується чекпоінтом із ДВОМА дорогами — «До плану
  курсу» (сторінка курсу тоді рендерить `CourseReview` із планом і датою
  відкриття) і «На головну».
- **Типи питань (2026-09-17).** Оцінювані типи —
  `SCORED_COMPONENT_TYPES` у `lib/componentTypes.js`: `quiz`, `hotspot`,
  `ordering` (розставити кроки), `matching` (зіставити пари). Усі дають
  ОДИН булевий результат: часткового балу в системі немає свідомо
  (`scoreForSegment` рахує кількість `answers[id] === true`), і додавати
  його — це переробка всього ланцюга підрахунку плюс полів у базі.
  Новий тип питання = значення в enum `ComponentType` у schema.prisma
  (інакше база відкине запис) + рядок у `COMPONENT_TYPES` і
  `SCORED_COMPONENT_TYPES` + `defaultContentForType` + поля в
  `AdminCourseEditor` (`ComponentTypeFields`) + рендер у
  `components/QuestionScreens.tsx` + гілка в `ScreenComponentBlock` і в
  `PreviewQuiz`. Нові типи зроблено БЕЗ перетягування (стрілки й тапи):
  застосунок телефонний, drag на дотику промахується.
  **Розбір по варіантах** — `options[].explanation` у quiz: показується
  після відповіді для обраного невірного й для правильного. Це впливає
  на запам'ятовування сильніше за формат питання, тож у нових питаннях
  заповнювати варто саме його, а не лише загальне `explanation`.
- **Аналітика складності питань.** `QuestionAnswer` — рядок на кожну
  відповідь (не upsert), пишеться в `module-complete` з перевіркою, що
  компонент належить саме цьому модулю. Частка правильних по кожному
  питанню віддається `GET /api/admin/courses/:id/question-stats` і
  показується прямо в списку компонентів конструктора (червоніє нижче
  50%) — сигнал автору, що питання незрозуміле або матеріал його не
  пояснює.
- **План курсу — мобайл-фьорст, резина (2026-09-17).** Поріг сітки —
  `@container cp-card (min-width: 640px)`, той самий, що й у плашок
  фактів (геометрія самої дороги/карток — вище, «Показ плану, четверта
  ітерація»). Вступний екран (`.cp-intro`) і кнопки під ним (`.navbar`)
  на цій же ширині розтягнуті на 100% картки (не на власні 960px, як
  решта екранів курсу) — плану з десятком модулів завузько на 960px, а
  кнопки під ним мають бути тієї ж ширини, що й контент над ними.
  Плашки «екранів/питань/хв» і банер «Пройдіть на 100%!» над планом
  прибрано — дублювали сам план гірше за нього ж. Час на курс і статус
  сертифіката тепер усередині плану: `lib/coursePlan.ts
  appendRemainingTime`/`certificateStatus`, факт «Сертифікат» у
  `components/CoursePlan.tsx` («Отримано» — курс складено і КОЖЕН модуль
  на 100%, не лише пройдено прохідний бал).
- **Підказки в конструкторі.** Просте керування — `title=` в один рядок;
  правило, яке в рядок не вміщається — `HintDot` («ⓘ», текст у `data-hint`,
  показ по ховеру й по фокусу з клавіатури). Тексти полів курсу лежать
  однією мапою `HINTS` у `components/AdminDashboard.jsx` — одне джерело на

  розходяться. Нове поле в конструкторі = рядок у `HINTS` + `HintDot`
  поруч із підписом.
- **`Course.targetPositions`/`targetTerritories`/`publishAt`** — це лише
  ЗБЕРЕЖЕНИЙ НАМІР. Сам по собі не створює жодного `Enrollment`. Реальне

  десятки запитів на хвилину) і upload фото; журналюються створення/

## Кабінет керівника та хаб

- Кабінет керівника: рейтинг команди (`lib/rating.ts getTeamRating` →
  `computeTeamRating`) — один зріз по всій компанії (усі активні + groupBy
  журналу), а не BFS на кожного керівника; % від найкращого у своїй посаді,
  середнє команди, місце серед команд керівників тієї ж посади.
- `/hub/learn` — не плаский список, а `lib/progress.js groupLearning`:
  обов’язкові (прострочені → дедлайн) → рекомендовані → пройдені.
- **Бали (`RatingEvent`) ДЗЕРКАЛЯТЬ поточний стан, а не історію**
  (рішення користувача 2026-09-19, після того як він додав балів у
  /admin/badges і вони «не пересчитались»). Журнал більше не
  append-only: `lib/rating.ts syncEnrollmentEvents(enrollmentId)` і
  `syncBadgeAwards(badgeId)` приводять свою частину журналу до бажаного
  стану (створити / змінити ціну / прибрати). Будь-яка нова точка, що
  міняє результат курсу або відзнаку, кличе саме їх, а не «дописати, чого
  нема»: інакше знову з'являться бали за скинутий курс і відзнака, що
  коштує 1000 у списку й 100 у сумі. `RatingEvent` посилається на
  enrollment/badge через `refType`/`refId` БЕЗ foreign key — каскаду
  нема, при видаленні прибирати бали вручну (див. DELETE-роути
  enrollments/badges).
- **Ціна відзнаки** — `Badge.points`, а для ручної відзнаки без власних
  балів — правило `manual_badge_default` (`lib/ratingLogic.ts
  badgePoints`). Показувати в UI саме `badgePoints()`, не сире поле.
- **Сертифікат = РІВНО 100%** (`Enrollment.scorePercent === 100`, у плані —
  кожен модуль на 100%), один критерій на всі чотири місця: список у
  «Досягненнях» (`lib/achievements.ts`), PDF-роут
  (`app/api/courses/[slug]/certificate`), статус у плані курсу
  (`lib/coursePlan.ts certificateStatus`) і фінальний екран плеєра
  (`CompleteScreen` у `components/CoursePlayer.jsx`, `showCertificate`).
  Історія планки: до 2026-09-19 — рівно 100%; 2026-09-19 опустили до
  просто "складений курс" (`Enrollment.passed`, скарга користувача
  «Сертифікати должно быть больше»); 2026-09-22 користувач повернув назад
  до 100% («Сертификат только 100% пройденый курс», курс на 83% у плані
  показував "Сертифікат: Отримано" — визнано багом). Новий поріг додавати
  лише в усі місця одночасно.

## Сповіщення (центр + Web Push)

- **Одна точка входу** — `lib/notifications.js notifyEmployees(ids, event)`:
  фільтр за вподобаннями (`NotificationPreference`, дефолт — усе
  увімкнено) → рядки `Notification` (центр сповіщень; `dedupeKey @unique`
  + `createManyAndReturn(skipDuplicates)` роблять будь-який cron
  ідемпотентним) → Web Push на всі `PushSubscription` адресата
  (`lib/webPush.js`, бібліотека `web-push`, VAPID). Push — лише доставка;
  джерело правди — рядок у БД, тож людина без дозволу на push (або на iOS
  без встановленої PWA) усе одно бачить подію в центрі.
- **Події** (тип → категорія у `lib/notificationTypes.js`): призначення
  курсу (`lib/courseAssignment.js enrollEmployees`), нагадування за 3/1
  день і прострочення (cron), ачивки авто/ручні, денний дайджест
  керівнику по прямих підлеглих (cron), ручна розсилка з
  `/admin/notifications` (`Broadcast`). Усе — best-effort у `try/catch`:
  збій доставки ніколи не відкочує бізнес-дію.
- **Секрети:** `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`
  (`mailto:…`) — генерує й вписує в .env/Vercel користувач:
  `npx web-push generate-vapid-keys`. Без них `isPushConfigured()` → false,
  push мовчки вимкнено, центр працює.
- **Telegram** (`lib/telegram.ts`, `lib/telegramLogic.ts`, 2026-09-16) — другий
  канал доставки в тому ж `notifyEmployees`: після push шле в чат бота
  CarlsON усім з `TelegramLink`, у кого `NotificationPreference.telegram`
  не false. Прив’язка — deep link з профілю (`t.me/<bot>?start=<token>`,
  токен HMAC на SESSION_SECRET, 15 хв, без таблиці) → webhook
  `app/api/telegram/webhook` (перевіряє `TELEGRAM_WEBHOOK_SECRET`) робить
  upsert; `/stop` — відв’язати; інший текст — у `TelegramInbound` для
  адмінки. Bot API — прямі fetch, без бібліотеки. Зниклі чати (403/«chat not
  found») видаляються, як push 404/410. Адмінка: `/admin/notifications` →
  `AdminTelegram` (стан, webhook, прив’язки, тест, вхідні); розсилка
  обирає канали (`Broadcast.channels/pushed/telegramSent`). Без
  `TELEGRAM_BOT_TOKEN` канал мовчки вимкнено.
- **Клієнт:** `public/sw.js` (push/notificationclick/pushsubscriptionchange,
  без кешу), `lib/pushClient.js` (стан: unsupported / ios-not-installed /

## Логін співробітника

- PIN генерується заново при КОЖНОМУ запиті (не статичний), живе 12
  годин (`PIN_TTL_MS` у `lib/auth.js`). **6 цифр** (2026-10-05, було 4):
  `PIN_LENGTH` у `lib/pin.ts` — одне джерело для генератора, поля вводу,
  підказки на /register і тесту; `openapi.yaml` і демо-тур (6 клітинок)
  правляться разом із ним. Сервер приймає лише цифри довжиною 4…PIN_LENGTH
  (`PIN_FORMAT` у `app/api/auth/confirm/route.js`, те саме в `openapi.yaml`):
  нижня межа 4 — перехід, PIN, виданий до деплою, доживає свої 12 годин.
  Після 2026-10-07 звузити до рівно PIN_LENGTH у роуті, openapi і на /register.
- Провайдер PIN-листів — `EMAIL_PROVIDER` (`lib/mailer.js`): за замовчуванням
  Resend, `gmail` — Gmail SMTP, і локально, і на проді. Прод з 2026-09-15
  на Gmail: домен `carlsberg.ua` нам не адмініструвати, а Resend без
  підтвердженого домену шле лише на пошту власника акаунта.

- **Тестовий вхід** (`lib/demoLogin.ts`, кнопка зверху зліва на
  `/register`): увімкнено лише за `DEMO_LOGIN_CODES` (кома-список кодів
  демо-персон). Колега обирає кабінет (співробітник/керівник), персону зі
  списку і вказує СВОЮ пошту — `POST /api/auth/register` з `demoEmail`
  переадресовує PIN на неї (`requestLoginPin(..., { recipientOverride })`).
  Сервер відкидає `demoEmail` для кодів поза списком (403). У базі нічого
  не змінюється; на проді — увімкнути змінну у Vercel лише на час демо.

## Дизайн-система: токени UI-шкали і стенд

Розміри й форми атомів — ЛИШЕ через токени в `app/styles/tokens.css`
(2026-09-16, уніфікація після інвентаризації: 12 висот кнопок, 7 розмірів
іконкових, 3 реалізації таблиць, 24 пари паддингів карток):
`--radius-btn/-card/-input/-badge`, `--btn-h-sm/-md/-lg` + `--btn-px-*`,
`--iconbtn-sm/-md`, `--border-w`, `--card-pad(-compact/-roomy)`,
`--card-shadow`, `--table-cell-pad`, `--chart-bar-radius`,
`--chart-ring-w`, `--chart-ring-cap`. Правила:

- Кнопка = один із трьох розмірів (`min-height: var(--btn-h-*)`, горизонтальний
  паддинг `--btn-px-*`), іконкова — `--iconbtn-sm`/`-md` і `--radius-btn`;
  жодних власних 26/30/35/46px. Фокус — лише `box-shadow: var(--cb-focus-ring)`.
- Рамка — `var(--border-w) solid …`, не `1px`/`1.5px`. Картка — один із трьох
  паддингів-токенів; тінь карток — `--card-shadow`.
- Таблиця — лише справжня `<table class="admin-table">` (рядок-кнопка:
  `<tr class="adm-emp-row" role="button" tabIndex={0}>`); grid-«таблиці»
  з `<span>` більше не робити.
- Діаграма — форма кінців ЛИШЕ з токенів: будь-яка прогрес-смуга
  (`.mgr-bar-track/-fill`, `.ct-progress-*`, `.xp-*`, `.cp-progress-*`)
  бере `--chart-bar-radius`, кільце — `--chart-ring-w`/`--chart-ring-cap`
  через CSS, а не атрибутами `stroke-width`/`stroke-linecap` у JSX (SVG
  не приймає там `var()`). Кільце — спільний `components/CompletionRing.tsx`,
  один і в кабінеті керівника, і в прев'ю стенду; нової копії не робити.

## Верстка: сітки однотипних карток

Будь-який набір однотипних карток (курси співробітника, призначення в
кабінеті керівника, каталог) верстається спільним класом **`.card-grid`**
(`app/globals.css`) — не власною `grid`/`flex`-розкладкою в кожному місці.
Ширину картки задає `--card-min` на контейнері (дефолт 260px), крок —
`--card-gap`.

Три правила, зафіксовані там, — кожне з реального дефекту, не з естетики:

- **`auto-fit` + `minmax(min(100%, …), 1fr)`**, без ручних `@media`.
  `min(100%, …)` обов'язковий — без нього на вузькому екрані колонка стає
  ширшою за сторінку й з'являється горизонтальний скрол.
- **`grid-auto-rows: 1fr`** — усі картки однакової висоти, по найбільшій,
  і рядки рівні між собою теж. Картки кожна по своєму вмісту дають рваний
  нижній край, який читається як збій сітки. Якщо в картці є фінальна дія
  (кнопка внизу) — картка стає flex-колонкою, дія притискається
  `margin-top: auto`, інакше кнопки стоять на різних рівнях.
- **Усередині вузької картки текст ПЕРЕНОСИТЬСЯ, а не їде біжучим
  рядком.** `MarqueeText` розрахований на широкий одиночний ряд; у сітці
  він стартує на кожній картці одночасно, і в застиглій фазі назва
  виглядає обрізаною з початку (`«…аперечення щодо об'єму закупівлі»`
  замість `«Заперечення…»`). За одну сесію на цьому спіткнулись чотири
  рази поспіль — у сітці завжди звичайний перенос + `overflow-wrap:
  anywhere`.
  **Виняток — картки дашборда керівника** (рішення користувача
  2026-10-04): заголовки й підписи рядків діаграм завжди в ОДИН рядок із
  «…», а біжучий рядок — лише на вимогу (поки наведена миша / один прохід
  після тапу; перший тап по обрізаному підпису-посиланню не переходить):
  `lib/onelineMarquee.ts` + блок «Однорядкові підписи» в `manager.css`.
  Розміри карток — як цеглинки (`lib/dashboardHeights.ts`): ширина лише
  ¼/½/уся (3/6/12 колонок, мінімум за змістом — `minCardW` у
  `ManagerDashboard.jsx`), висота лише S або L = 2×S з проміжком
  (`standardRows`, `CARD_S_PX`), довгі списки скроляться в межах L.
  Дір у сітці не буває: після кожної зміни `fitCards` ущільнює, а що не
  закривається — `holeFillSteps` (розширити ¼→½/½→усю, S→L, вирівняти
  смугу, перенести картку в діру, непарну S зі смуги — під неї на всю
  ширину); тому ширина картки може змінитись сама. Але це тимчасово: власна
  ширина картки (дефолт або з ручки) зберігається окремо — поле `pw` у
  localStorage — і при вмиканні/вимиканні карток і зміні ширини все
  перепаковується від неї. На F5 розкладка відновлюється як збережена, без
  перепакування. На телефоні — висота по вмісту.
  **Повернення з телефонної ширини (2026-10-05):** gridstack при 1 → 12
  колонок сам перераховує позиції (moveScale) і збиває порядок, а `change`
  записав би це в localStorage. Тому `saveLayout` мовчить 600 мс після
  `resize` вікна, а спостерігач, побачивши перехід 1 → 12 (`prevCol`),
  пересоздає сітку (`setStoredGrid(readStoredGrid())` + `gridEpoch`) — як
  після F5. Точковий `grid.load` після цього НЕ тримається: наступний
  `fitCards` бачить «діри» й розтягує сусідів на 12 колонок.
  **Картка на всю ширину (матриця «люди × курси») — висота рівно по вмісту**
  (`fitCards`: `n.w >= GRID_COLUMNS`), а не S/L: сусідів по ряду нема, і L давала
  порожнечу зверху й знизу (скарга 2026-10-05); `holeFillSteps` такі картки не
  «достроює». **Повторний показ вкладки (Next Activity)** заново запускає ефекти
  дашборда: сітку пересоздають, але (1) `visibleSigRef` пропускає перепакування від
  власних ширин, якщо набір карток не змінився; (2) джерело розкладки — свіжий
  `readStoredGrid()`, не застарілий стан; (3) модульний `settledGrid` (x,y,w,h
  після останнього `fitCards`) вантажиться одразу з висотами — інакше всі картки
  стартують з 2px і «ростуть» по одній (13 оновлень, кожне зсуває решту); (4) CSS-анімація
  сітки (`setAnimation`) вимкнена, вмикається лише на 600 мс після жесту людини —
  інакше кожен перерахунок запускав 0.3s-перехід, спостерігач розмірів реагував на кожен
  кадр і перерахунок йшов по колу. Заміри (headless Edge, CPU ×4, всі 13 карток,
  повернення на «Команду»): було 3.1–5.6 с, стало 1.7–2.7 с; з 6 картками 1.8–2.3 → ~0.9 с.
  Залишок — перерахунок стилів у `fitCards` (клас `is-measuring` на всю сітку, двічі за прохід).

**Дрібні правки з iPhone (2026-10-05).** Картка курсу в сітці: усе під
описом (термін, прогрес, «Залік · N%») притиснуте донизу ланцюжком flex
(`manager.css`, `.card-grid .course-tile`), у ряду ці блоки на одній лінії над
кнопкою; опис не обрізаємо. Числа (`CountUp`) мають `playKey` — кружляють лише
при ПЕРШОМУ показі за завантаження сторінки (профіль «Бали/Рейтинг/Нагороди»,
«Мій прогрес», «Досягнення»; `TeamStatusBar` — проп `instant`). Кружок зі звездою
рівня (`.lv-star`) — один для профілю, «Мій прогрес» і «Досягнень»: `flex:none`
+ SVG-маска замість символу «★» (шрифт зсував його вниз, а `inline-block` у
flex-контейнері стискав кружок в овал). Списки зі смугами в картках дашборда не
скролляться вбік (`overflow-x:hidden`): прозорі поля маски `number-flow` виходять
за ячейку на ~6px; що не влазить — однорядковий підпис із «…» і бігучим рядком.

**Таблиці «як у Excel» (2026-10-05).** Ширина колонок (межа заголовка) і
висота рядків (нижня межа першої клітинки) тягнуться мишею в УСІХ
таблицях застосунку, подвійний клік — скинути; розміри — localStorage,
окремо на кожну таблицю (`lib/tableSizes.ts tableKey`: шлях без id +
номер таблиці + заголовки). Один `components/TableSizes.tsx` у кореневому
layout — нічого не вставляє в розмітку (делегування подій + inline
width/height), тож нова таблиця отримує це сама. Журнал дій і матриця
мають власну реалізацію (`.audit-grid`, `.mgr-matrix`); таблиці без неї —
атрибут `data-no-resize`. Рядок із `data-row-key` зберігає висоту за ним,
інакше — за номером. Миша: зона біля межі 6px; **палець** (2026-10-05,
скарга з iPhone): зона 16px (`TOUCH_EDGE`), `touchstart` у ній скасовує
скрол, скинути — подвійний тап по межі. Ручки матриці на `pointer: coarse`
— 24px (`manager.css`). Довге натискання ВСЕРЕДИНІ `<table>` на дашборді не
вмикає режим перетягування карток (`handleCardPointerDown`) — інакше тап по
межі матриці вмикав «трясіння» картки.

**Копіювання заборонене (2026-10-05).** `body { user-select: none }`
(globals.css) + `components/CopyGuard.tsx` (copy/cut/contextmenu/dragstart)
по всьому застосунку, крім полів вводу (PIN із листа, пошук, тексти
конструктора). Дані — лише кнопкою «Завантажити звіт»
(`components/ExportReportLink.tsx`: дашборд, /manager/team, картка людини).
Кнопки «Скопіювати» через `navigator.clipboard` працюють.

**Акордеон усередині картки сітки — не робити.** `grid-auto-rows: 1fr`
рівняє не сусідів у ряду, а ВСІ ряди сітки: розкриття однієї картки на
`/manager/courses` роздувало кожну картку сторінки (263 → 457px) і лишало
дірки в середині сусідніх (скарга користувача, 2026-09-17). Список
модулів із картки прибрано зовсім — його повніша версія вже є планом
курсу в плеєрі (`components/CoursePlan.tsx`): там ще й дати відкриття,
графік і кнопки перепроходження. Якщо деталі в сітці колись знову
знадобляться — розгортати ПІД усією сіткою (як `CourseExpandedBody` в
/admin) або в бічній панелі, але не всередині плитки.
Смуга на картці курсу показує ПРОГРЕС (складено N з M модулів,
`lib/progress.js moduleProgress`), а не бал: до 2026-09-17 там стояв
`courseTileStatus().pct`, який у незавершеного курсу завжди 0, і курс із
одним складеним модулем із десяти виглядав незрушеним.

Виняток — `/hub` і плеєр: вони сверстані під телефонну ширину, там
стовпчик карток один за одним правильний. Сітка — для десктопних
екранів (`/manager`, `/admin`).

Якщо той САМИЙ компонент показується і там, і там (`CourseTile` — і в
телефонній рамці `/hub`, і в сітці `/manager/courses`), його внутрішня
адаптація робиться **`@container`, а не `@media`**: у `/hub` картка
живе всередині вузької рамки на широкому десктопному вікні, тож
медіа-запит по ширині вікна там ніколи не спрацює. Той самий висновок
уже зроблено для плеєра (`@container cp-card`, `course-player.css`) і
для картки курсу (`@container ct-card`, `hub.css`). Пам'ятай, що
`container-type: inline-size` міряє **content-box** — поріг у запиті
менший за зовнішню ширину картки на її padding і рамку.

Пояснення по ховеру (що рахує діаграма, що робить неочевидна кнопка) —
спільний `HintDot` (`components/HintDot.jsx` + `.hint-dot` у
`globals.css`), не власний tooltip і не нативний `title=`.

Сітки з ФІКСОВАНОЮ розміткою кількістю блоків (не за даними) — окремий
випадок: там `auto-fit` шкідливий, бо сам обирає число колонок і лишає
дірки в останньому ряду; задавай колонки явно й лише такі, на які
кількість блоків ділиться без залишку. Але спершу перевір, чи кількість
блоків справді фіксована: `.mgr-charts` (`app/styles/manager.css`) саме
так і жив (8 карток → 1/2/4 колонки, ніколи 3), доки керівник не отримав
перемикачі видимості карток (2026-09-19) — щойно кількість стала даними,
жорсткі колонки почали лишати півекрана порожнім, і блок повернувся до
звичайного `auto-fit`.

## Робочий процес

- Міграції на таблицях із реальними даними — скіл `/db-migrate`
  (create-only → ручна правка SQL при потребі → `migrate deploy`,
  ніколи `migrate reset`/`db push --accept-data-loss` без явного дозволу
  користувача).
- **Опис API — `openapi.yaml`** у корені (2026-10-04). Новий, перейменований
  чи видалений Route Handler = правка цього файлу в тому ж PR: `lib/openapi.test.ts`
  звіряє його з `app/api/**/route.*` (шлях + метод) і валить CI при розбіжності.
  Повні схеми тіл — для зовнішніх контрактів (`/api/data/*` Power Query, Telegram,
  cron, health) і плеєра (answer, module-complete); решта — шлях, авторизація, коди.
  `oasdiff` у CI (job `api-diff`) позначає ламаючі зміни в диффі PR. Перегляд —
  Swagger UI на `/admin/api` (`components/ApiDocs.tsx`, пакет `swagger-ui-dist`).
- Одноразові скрипти для перевірки/діагностики — `scratch-*.js` у корені
  проєкту, видаляти одразу після використання (не комітити).
- **Локальні робочі матеріали (презентації, документи для керівництва,
  чернетки) — поза git, назавжди.** Їхні теки перелічені в `.git/info/exclude`
  (локальний файл, не `.gitignore` — щоб назви не світились у репо). Бо на
  іншому комп'ютері цього файла нема, `.husky/pre-commit` ще й відхиляє коміт
  із файлами в НЕВІДОМІЙ теці верхнього рівня та будь-яким офісним документом
  (`.pptx/.docx/.xlsx/.pdf`). Нова справжня тека проєкту = рядок у `allowed`
  там. Перевірено 2026-10-05: жодного такого файла в історії всіх гілок нема.
- **Комітити/пушити — ЛИШЕ на пряму команду користувача, щоразу окремо.**
  Дозвіл «закоміть» стосується одного коміту, не сесії; «перенеси в
  гілку», «зроби», «перевір» — це НЕ дозвіл на коміт. Після правок —
  зупинитись і спитати «комітити?». 2026-09-15 за одну сесію так пішло
  шість комітів без запиту — користувач попросив записати це правило
  жорстко.

### Само-оптимізація: помічаєш повторення — пропонуй скіл

Якщо в межах ОДНІЄЇ сесії доводиться вручну повторити ту саму
багатокрокову послідовність команд 3+ рази (не одну команду — саме
послідовність: наприклад "убити node → почистити .next → підняти dev"
або "create-only → правка SQL → migrate deploy → generate → перевірка")
— зупинись і запропонуй користувачу оформити це як `.claude/skills/`
проєкту, за прикладом `restart-dev`/`db-migrate` (вони самі з'явились
саме так — 15+ ручних перезапусків dev-сервера за одну сесію). Не чекай,
поки попросять: коротко опиши, яку послідовність пропонуєш зафіксувати,
і чому саме зараз (яка повторюваність це показала) — рішення лишається
за користувачем, ти лише помічаєш патерн і пропонуєш.

Це стосується не тільки shell-команд: та сама логіка — якщо тричі
пишеш майже однаковий `scratch-*.js` для однієї й тієї ж перевірки
(порахувати щось, звірити стан після дії) — це теж кандидат або на
скіл, або на постійний (не scratch) скрипт у `prisma/` чи `lib/`.
